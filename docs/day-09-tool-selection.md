# Day 9：不是每個按鈕都該變成 Tool

候選能力必須先通過任務價值、穩定性、上下文需求與副作用四個判準。分數不是自動決策，而是迫使設計者說清楚取捨。

| 候選操作 | 任務價值 | 穩定性 | 上下文需求 | 副作用 | Day 9 決定 |
|---|---:|---:|---:|---:|---|
| `search_events` | 高 | 高 | 低 | 無 | 保留為讀取型候選。 |
| `get_event_details` | 高 | 高 | 中 | 無 | 保留，之後以目前查看的活動為情境。 |
| `save_event` | 中 | 高 | 中 | 有 | 保留，但須先處理可見狀態與人類確認。 |
| 開啟篩選器 | 低 | 低 | 高 | 無 | 淘汰；這只是 UI 步驟。 |
| 展開活動卡片 | 低 | 低 | 高 | 無 | 淘汰；它沒有獨立任務價值。 |
| 按下搜尋按鈕 | 低 | 低 | 高 | 無 | 淘汰；應提供「搜尋」而不是每個實作步驟。 |

## 篩選原則

1. 一個 Tool 要對應使用者可說出口的目標，而不是 UI 控制項。
2. 需要大量頁面位置、視覺文案或暫態焦點才有意義的操作，通常不是好的 Tool。
3. 有副作用的能力不能因為「可呼叫」就直接交給 Agent；它還需要人類確認與可見回饋。

本日只做選型，不註冊任何 Tool。下一篇才比較 Declarative API 和 Imperative API。
